# Matrix key recovery and continuity drill

This runbook covers the generated Matrix secret used by Synapse and MAS. It
does not contain secret material and must not be used to restore into the
production namespace.

## Current ownership and consumers

`matrix-generated` is created in-cluster by the ESS `matrix-init-secrets` Job
(`matrix-tools:0.10.4`). It is not an `ExternalSecret`, SOPS/age object, or
CNPG secret. The Secret is mounted read-only by the Synapse StatefulSet and
the MAS Deployment, including their configuration/migration init containers.

The live rendered configuration establishes this key-to-consumer map:

| Key | Consumer | Use | Recovery class |
| --- | --- | --- | --- |
| `SYNAPSE_SIGNING_KEY` | Synapse main and config-check hook | Synapse signing identity | Stable, indispensable |
| `MAS_SYNAPSE_SHARED_SECRET` | Synapse main/config-check hook and MAS | Synapse/MAS shared authentication | Stable, cross-service |
| `MAS_ENCRYPTION_SECRET` | MAS | MAS encrypted state | Stable, indispensable |
| `MAS_RSA_PRIVATE_KEY` | MAS | MAS signing key | Stable, indispensable |
| `MAS_ECDSA_PRIME256V1_PRIVATE_KEY` | MAS | MAS signing key | Stable, indispensable |
| `SYNAPSE_MACAROON` | Synapse main/config-check hook | Macaroon/token signing | Stable for token continuity; rotation has impact |
| `SYNAPSE_REGISTRATION_SHARED_SECRET` | Synapse main/config-check hook | Registration/admin bootstrap credential | Regenerable only with an explicit rotation decision |
| `SYNAPSE_EXTRA` | Synapse config-render init container | Additional homeserver configuration | Regenerable only after rendered-config review |

The MAS OIDC client material is separate: `matrix-mas-oidc` is owned by ESO
and re-materialized from Doppler. CNPG connection credentials and the S3
credentials are also ESO-owned. They are not substitutes for the stable
Matrix signing/encryption keys.

The current `matrix-generated` Secret exposes the expected key names only and
has no owner reference. Synapse and MAS reference the expected generated and
ESO-owned Secret objects through their rendered configuration. Secret values,
decoded data, and fingerprints are deliberately absent from this repository.
The selector intentionally excludes `app.kubernetes.io/managed-by`: the
rendered Job uses `Helm`, while the existing generated Secret retains a
different historical manager label. The stable five-label selector matches
exactly one live Secret and must be rechecked against the selected backup
inventory before restore.
The `matrix-init-secrets` Job completed after the selected Velero backup, so
the backup is not accepted as proof of the bytes currently mounted by the
workloads. The durable key status therefore remains `NOT_PROVEN` until the
operator-held baseline and the isolated selector-scoped restore both exist.

Longhorn is an additional media recovery source, not a replacement for
Velero/Kopia or CNPG/Barman. The media PVC carries the explicit
`persistent-offsite-backup` and `source` labels, and the completed backup is
recorded as evidence; no production PVC, PV, volume, or recurring job was
modified by this runbook.

## Approved isolated procedure

Before execution, PLT-92 must record approval, the UTC window, the selected
completed backup, and an independent reviewer. The operator must use a fresh
namespace and must not restore into `matrix`.

1. Create an isolated namespace with default-deny ingress and egress. Permit
   only the API calls and internal test traffic needed for the validation Job;
   do not create an HTTPRoute, public Service, federation egress, or OAuth
   callback.
2. Preflight the installed Velero CLI and confirm that `restore create`
   supports label selectors. Restore only the `matrix-generated` object from
   the selected completed backup with `--include-namespaces matrix`,
   `--include-resources secrets`, an explicit namespace mapping from
   `matrix` to the isolated namespace, and this existing unique selector
   matching the stable ESS labels shared by the live Secret and rendered Job:
   `app.kubernetes.io/instance=matrix-init-secrets,app.kubernetes.io/part-of=matrix-stack,app.kubernetes.io/component=matrix-tools,app.kubernetes.io/name=init-secrets,app.kubernetes.io/version=0.10.4`.
   Verify in the selected backup inventory that this selector matches exactly
   one object named `matrix-generated` before creating the restore. A resource-
   type filter for `Secret` alone is insufficient because it could restore
   OIDC, CNPG, or S3 credentials. After the restore, assert that exactly one
   Secret named `matrix-generated` exists in the isolated namespace before
   mounting it. If the installed Velero version cannot apply this selector,
   stop and use an approved compatible tool or extraction path; never fall
   back to an unfiltered Secret restore. Do not restore the production
   namespace in place and do not restore PVCs for this key-only test.
3. Verify only metadata and key names with `kubectl`; never print Secret YAML,
   decoded data, environment dumps, or application logs that may contain
   credentials.
4. Run a short-lived validation Job that mounts the restored Secret read-only
   and emits only SHA-256 fingerprints for the named files. Compare those
   fingerprints with an operator-held baseline captured through the same
   protected path. Store the result as restricted drill evidence, not in Git
   or a public ticket.
5. Delete the validation Job and namespace only after PLT-92 records the
   result and approves cleanup. If cleanup is not approved, retain the
   isolated resources with an explicit expiry and owner.

The fingerprint test is a continuity check, not an application restore proof.
The Matrix application drill additionally needs isolated CNPG recovery,
isolated media, compatible configuration, and an internal Synapse/MAS smoke
test. No RPO/RTO or `MATRIX_APP_RESTORE=PASS` may be inferred from the key-only
test.

## Isolated CNPG, media, and application recovery plan

This procedure is prepared only. It must not be started until PLT-92 records
the approver, a UTC window, the selected completed backup names, the expected
cost bound, and the independent reviewer. It creates new names in a new
namespace and never changes `matrix`.

1. Record `T0` in UTC, the Velero backup completion time, the two CNPG backup
   completion times, the Longhorn media backup completion time, and the latest
   known application write marker. Confirm all source artifacts are retained.
2. Create a namespace such as `dr-matrix-YYYYMMDDHHMM` with default-deny
   ingress and egress. Do not create an HTTPRoute, public DNS record, public
   Service, federation egress, Authentik callback, or production identity
   binding. Use only ClusterIP services and allow-listed test traffic.
3. For each database, create an isolated Barman `ObjectStore` that points to
   the existing recovery prefix and uses an ESO-created credential Secret by
   key reference; do not copy or print credential values. Create a new CNPG
   `Cluster` with `bootstrap.recovery.source` and an `externalClusters.plugin`
   entry for `barman-cloud.cloudnative-pg.io`. The source mapping is pinned as
   follows, and must be checked against the live `Backup.status.backupId`
   immediately before the drill:

   | Target | Source `serverName` | Recovery ObjectStore | Backup CR | `recoveryTarget.backupID` |
   | --- | --- | --- | --- | --- |
   | Synapse | `matrix-synapse-postgresql` | `matrix-synapse-hetzner-store` | `matrix-synapse-postgresql-gap-remediation-20261020` | `20261020T151710` |
   | MAS | `matrix-mas-postgresql` | `matrix-mas-hetzner-store` | `matrix-mas-postgresql-gap-remediation-20261020` | `20261020T151710` |

   If the live `backupId` differs, stop and record the newly selected value;
   never let the plugin silently choose the newest backup. Keep the target's
   `spec.plugins` section enabled only if WAL archiving is intentionally
   required for the drill. This is a new cluster bootstrap, not an in-place
   restore. The official plugin recovery shape is documented at
   https://cloudnative-pg.io/plugin-barman-cloud/docs/usage/.
4. Pin each recovery to the selected `recoveryTarget.backupID` above. Wait for
   both isolated clusters to report Ready, then run read-only SQL
   sentinels: database identity, schema/table presence, row counts for the
   Matrix event/state tables, and a transaction-consistency check. Record
   command exit status and timestamps, not credentials or full user data.
5. Restore media only from the selected completed Longhorn backup into a new
   Longhorn volume/PVC in the drill namespace. Mount it read-only for the
   inventory phase, record file count/size and a small approved sentinel set,
   then use a writable copy only if the application compatibility check
   requires it. Never mount the production PVC into the drill namespace.
6. Restore `matrix-generated` with the selector-scoped procedure above, then
   provide only the restored key files to isolated Synapse and MAS validation
   pods. Start no public listener. Validate that the stable key set, database
   schema, media paths, and configured `server_name` agree before running the
   internal smoke.
7. Run the application smoke entirely inside the namespace: Synapse health
   and config check, MAS health and local account/session check, one test room
   create/send/read cycle, and media upload/read against the restored copy.
   Disable federation and external OAuth callbacks. Do not reuse production
   identities, domains, access tokens, or room IDs for serving traffic.
8. Record `T1` restore submission, `T2` first Ready for both CNPG clusters,
   `T3` first successful SQL/media sentinels, and `T4` successful internal
   application smoke. `RTO = T4 - T1`. `RPO` is the UTC distance from the
   latest accepted durable source point (`T0`/selected backup or approved
   PITR target) to the latest verified application write marker. If no
   application write marker exists, report `RPO=NOT_MEASURED`, not zero.
9. Preserve the evidence outside the production namespace. Cleanup is a
   separate approved action restricted to the exact drill namespace, PVCs,
   PVs, Longhorn volumes, Services, Jobs, and CNPG resources created for this
   run. Existing `dr-matrix-media-20261020` and other restore residue are not
   owned by this runbook and must not be removed implicitly.

### Scope and failure gates

Before the key-only restore, verify with the installed Velero CLI that
`restore create` supports `--selector`, `--include-resources`,
`--include-namespaces`, `--namespace-mappings`,
`--include-cluster-resources=false`, and `--restore-volumes=false`.
Preflight the selected backup inventory and require exactly one object named
`matrix-generated` matching the five-label selector. Use
`--existing-resource-policy=none`; fail if any object outside the selector,
namespace mapping, or Secret resource filter is planned. After the restore,
enumerate the restored namespace and compare the complete `(apiVersion,kind,
namespace,name)` set to the single expected Secret before mounting it. A
Secret count other than one, a selector mismatch, a restored key mismatch, a
CNPG recovery error, or any attempted production endpoint is an immediate
`FAIL` and stops the drill.

`CNPG_RECOVERY=PASS` requires both isolated clusters to reach Ready and pass
the SQL sentinels. `MEDIA_RECOVERY=PASS` requires the restored Longhorn volume
to mount and pass the approved inventory/sentinel checks. `KEYS_CURRENT` is
metadata-only; `KEYS_DURABLE=PASS` requires the protected baseline and the
selector-scoped restore. `MATRIX_APP_RESTORE=PASS` additionally requires the
internal Synapse/MAS and room/media smoke. A completed backup, a successful
static render, or a healthy production workload alone cannot set any of these
application restore gates to PASS.

## Acceptance gates

- `SIGNING_KEYS_RECOVERABLE=PASS` only when all stable key fingerprints match
  the approved baseline and isolated Synapse/MAS configuration validation
  accepts the restored files without starting public listeners or making
  external callbacks. A fingerprint-only run is not enough to establish
  consumer usability.
- `SIGNING_KEYS_RECOVERABLE=NOT_PROVEN` when the Secret is merely present in a
  backup inventory, when the baseline is absent, or when the restore was not
  executed.
- Any mismatch in a stable key is a drill failure and must stop before
  starting Synapse or MAS. A pre-approved rotation of a regenerable key must
  be recorded separately and is not evidence of restore continuity. Do not
  regenerate or replace production keys as a workaround.
- The result must record source backup identity, UTC timestamps, namespace,
  reviewer, and cleanup decision without recording secret values or hashes in
  public evidence.
